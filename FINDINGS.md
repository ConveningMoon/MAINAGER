# FINDINGS — технический аудит Agent API

Дата измерений: **28.07.2026**. API version `1.0.0` (`GET /health`), MCP server
`vibemarketolog` `1.1.0`, протокол `2025-06-18`.

## Метод

Всё ниже — измерения против рабочего API, не чтение документации. Ключ с
правами `read` + `generate`. Каждая цифра воспроизводима командой из приложения.

Аудит выполнен **без единого платного вызова**: баланс 600 ₽ до и 600 ₽ после,
`daily_spend_today: 0`. Использовались `GET`-эндпоинты, `POST /generate/estimate`,
`POST /webhook-test`, `POST /safety-check` и оба MCP-эндпоинта. Это существенно:
всё, что описано ниже, ваш собственный API отдаёт бесплатно — но отдаёт в полях,
на которые агент не смотрит.

Там, где число получено моделированием, а не измерением, это указано прямо в
строке вместе с допущением.

## 1. `strict` не выражен в MCP-интерфейсе

Самый дорогой разрыв. Он же — самый дешёвый в исправлении.

### Что происходит

Ваша документация называет одну ошибку самой частой и объясняет, чем она
кончается:

> «Самая частая ошибка агентов — слать `image_input` для видео. […] Видео-модели
> его не читают → вы получите чистый text-to-video, а деньги спишутся.»
> — `/docs/agent-api`

И там же даёт средство защиты:

> «Без `strict` запрос выполнится, но в ответе появится поле `ignored_params` со
> списком отброшенных полей.» — `/docs/agent-api`

Средство работает. Проверено (§2). Но в MCP-интерфейсе его **нет в схеме**:

```
estimate_generation  properties: type, model, prompt, params
                     required:   [type, model]
generate_content     properties: type, model, prompt, params,
                                 webhook_url, idempotency_key
                     required:   [type, model]
```

Поле `params` описано как «Параметры модели из `list_capabilities`
(`aspect_ratio`, `image_urls`, `duration`, `quality` и т.д.)» — то есть как
параметры *модели*. `strict` не параметр модели: это флаг уровня запроса.

Он не упомянут:

- в `inputSchema` обоих инструментов;
- в описаниях инструментов;
- в поле `instructions` MCP-сервера, где расписан весь рекомендуемый сценарий:
  `list_capabilities → estimate_generation → подтверждение пользователя →
  generate_content с idempotency_key → get_generation_status`;
- на странице `vibemarketolog.ru/connect`, которой вы этот коннектор рекламируете.

### Доказательство

Один и тот же запрос через `estimate_generation`, MCP:

| Аргументы | Ответ |
|---|---|
| `params: {image_input: [...]}` | **`valid: true`**, `rejected: ["image_input"]`, `estimated_cost_rub: 196` |
| `params: {image_input: [...], strict: true}` | `valid: false` |
| `strict` как аргумент верхнего уровня | `valid: false` |

Защита достижима — угадыванием недокументированного ключа внутри свободного
объекта. Агент читает схему. В схеме этого ключа нет.

### Последствия

Сценарий по умолчанию через ваш MCP-коннектор — незащищённый. Агент, который
честно следует `instructions`, вызовет `estimate_generation`, получит
`valid: true`, покажет пользователю смету 196 ₽, получит подтверждение и спишет
196 ₽ за видео, которое проигнорировало картинку.

Измерено: **196 ₽ за один такой вызов** (`grok-ttv-10`). Умножение на объём
оставляю вам — своих цифр по трафику коннектора у меня нет.

### Предложение

Добавить `strict` в `inputSchema` обоих инструментов, значение по умолчанию
`true`. Это одна строка JSON Schema на инструмент. Как минимум — упомянуть его в
`instructions`, где уже описан весь остальной сценарий.

## 2. `/generate/estimate` отвечает `valid: true` на запрос, который сам же бракует

То же самое на уровне REST, и здесь дефект в контракте, а не в документации.

### Доказательство

`POST /generate/estimate`, тело с `image_input` для видео-модели, без `strict`:

```json
{"valid": true, "dry_run": true, "model": "grok-ttv-10", "type": "video",
 "estimated_cost_rub": 196, "balance": {"current": 600, "after": 404},
 "rejected": ["image_input"],
 "warnings": ["image_input is for type=image only. For image-to-video use
   image_urls[] with veo/kling/grok, first_frame_url with seedance, or
   character_image_url + reference_video_url with motion-control."]}
```

`valid: true` и `rejected: ["image_input"]` — в одном ответе.

С `strict: true` тот же запрос даёт `valid: false`.

### Последствия

Поле `valid` — единственное, на которое агент будет ветвиться: оно булево и
называется «valid». Вся информация для отказа у вас есть и вы её отдаёте в
`rejected` и `warnings` рядом. Но контракт говорит «годен».

Это не отсутствие проверки. Это проверка, результат которой не доведён до поля,
по которому принимается решение.

### Предложение

При непустом `rejected` возвращать `valid: false` независимо от `strict`, а
`strict` оставить управляющим поведением `/generate`, а не dry-run. Либо ввести
отдельное поле — `valid_strict` или `would_charge_for_ignored` — чтобы не ломать
существующих клиентов.

## 3. `price` в `/capabilities` — не цена вызова

### Доказательство

`/capabilities` отдаёт для `grok-ttv`:

```
price: 36
tiers: [grok-ttv-10, grok-ttv-20]
tier_prices: {grok-ttv-10: 196, grok-ttv-20: 316}
price_note: "price = цена при дефолтных параметрах; итог зависит от duration/тира
             — сверяйтесь с tier_prices или POST /generate/estimate"
```

Измерено через `/generate/estimate`:

```
grok-ttv 36 ₽ · grok-ttv-10 196 ₽ · grok-ttv-20 316 ₽ · grok-ttv-30 436 ₽
```

### Последствия

Модель стоимости, читающая `price` и останавливающаяся на нём, занижает счёт
**до 12×** (36 против 436). `price_note` об этом предупреждает, но предупреждение
— это строка на русском внутри JSON, а не поле, на которое можно опереться кодом.

### Предложение

Переименовать `price` в `price_from` или `price_default`. Имя `price` в
машиночитаемом каталоге читается как цена, и никакой `price_note` этого не
перебьёт.

## 4. `/capabilities` и `/prices` расходятся

Два машиночитаемых источника, оба выглядят авторитетно, оба неполны.

### Доказательство

Сверка полных списков идентификаторов, 28.07.2026:

| Симптом | Кол-во | Идентификаторы |
|---|---|---|
| Генерируется, но не имеет цены в `/prices` | 5 | `seedream-5-pro`, `seedream-5-pro-edit`, `motion-control-720p`, `motion-control-1080p`, `el-sound-fx-v2` |
| Есть цена, но нет в каталоге | 6 | `grok-itv-30`, `grok-ttv-30`, `seedream-5-lite-edit`, `resize-2k`, `resize-4k`, `suno-voice-create` |
| Разная категория | 2 | `gemini-omni-audio` (voice / text), `gemini-omni-character` (image / text) |

### Последствия

Потолок бюджета, построенный по `tier_prices` из `/capabilities`, равен 316 ₽.
Реальный максимум — `grok-itv-30` за 436 ₽, и `/generate/estimate` его спокойно
считает. **Занижение потолка на 38%** — то есть ограничитель расходов, собранный
по вашему же каталогу, пропускает самый дорогой тариф.

`seedream-5-pro` при этом генерируется и корректно оценивается в 40 ₽ через
`estimate`, но в `/prices` его нет вовсе.

### Предложение

Считать `/generate/estimate` единственным источником цены — он оказался
единственным полным — и сказать это в документации прямым текстом. Списки в
`/prices` и `price` в `/capabilities` пометить как справочные.

## 5. `/capabilities` противоречит сам себе

### Доказательство

Один и тот же ответ `GET /capabilities`:

```
capabilities.getting_started.image_to_video : "grok-itv-10|20|30"
capabilities.models.video["grok-itv"].tiers : ["grok-itv-10", "grok-itv-20"]
```

Три тарифа в одном месте, два в другом. Отсутствующий — самый дорогой, 436 ₽.

### Последствия

Реестр моделей, собранный из `models[].tiers` (то есть из машиночитаемой части, а
не из текстовой подсказки), не будет знать о `-30`. Агент никогда его не
предложит, а whitelist, построенный оттуда же, отклонит валидный запрос.

### Предложение

Сгенерировать `getting_started` из того же источника, что и `models`.

## 6. `duration` тарифицируется плоско

### Доказательство

`POST /generate/estimate`, модель `grok-ttv-10`, меняется только `duration`:

```
duration= 1  → 196 ₽        duration=10  → 196 ₽
duration= 5  → 196 ₽        duration=15  → 196 ₽
```

`rejected` пуст во всех четырёх случаях, `duration` присутствует в
`valid_params`. То есть параметр принят, объявлен валидным и на цену не влияет.

### Последствия

Односекундный ролик стоит столько же, сколько пятнадцатисекундный: **до 15× за
секунду полезного видео**. Экономически верное поведение — всегда запрашивать
максимум длительности тарифа. Ни документация, ни каталог этого не говорят.

Отдельно: остаётся открытым, влияет ли `duration` на результат вообще, или
длительность целиком задаётся суффиксом тарифа, а параметр отбрасывается. Это
**гипотеза, а не измерение** — для проверки нужен платный вызов и `ffprobe` по
файлу. Если она верна, это дефект из §2 во втором месте: параметр объявлен
валидным и молча игнорируется.

### Предложение

Если длительность задаётся тарифом — убрать `duration` из `valid_params` для
grok-моделей или возвращать его в `rejected`. Если влияет — отразить в цене.

## 7. Каталог эндпоинтов и каталог моделей неполны

### Доказательство

`capabilities.endpoints` перечисляет 28 путей. Работают и отвечают 200, но в
списке отсутствуют:

```
GET /me   GET /health   GET /capabilities   GET /generations   GET /inbox
```

`/inbox` — заметнее прочих: на нём строится входящий канал.

В обратную сторону: `/docs/agent-api` описывает модели `omnihuman-1-5` и
`volcengine-lipsync` с их полями (`image_url` + `audio_url`, `video_url` +
`audio_url`). В `/capabilities` их нет — ни в `video`, ни в одной из четырёх
категорий. Всего каталог отдаёт 45 генеративных моделей.

Про «170+»: `/prices` возвращает `hidden_non_generation_keys: 88` с примечанием,
что чат, обучение чат-ботов и посекундные тарифы «billed elsewhere». 45 + 88 ≈
133 — то есть публичная цифра не выдумана, но **агенту доступны 45**, и корректная
модель стоимости строится на этом числе. Стоит развести эти две цифры явно, иначе
интегратор считает поверхность больше, чем она есть.

### Предложение

Генерировать `endpoints` из роутера, а не поддерживать вручную. Для моделей из
документации, отсутствующих в каталоге, — либо вернуть в каталог, либо убрать из
документации.

## Что работает хорошо

Чтобы список выше читался как аудит, а не как претензия:

- `POST /generate/estimate` бесплатен и точен. Он корректно оценил все модели,
  включая те, которых нет в `/prices`, и включая тарифы, которых нет в `tiers`.
  Это лучший эндпоинт в API.
- `pre_charge_validation` реальна: недоступный `image_urls` возвращает
  `{"ok": false, "code": "unreachable", "http": 404}` и сбрасывает `valid` в
  `false` — до списания и бесплатно.
- Ответ `estimate` содержит `balance.{current, after}` и
  `daily_spend.{limit, today, within_limit}`. На этом можно построить оценку
  стоимости целого сценария, не делая ни одного платного вызова.
- `POST /webhook-test` отдаёт реальную диагностику доставки и формулу подписи —
  весь webhook-путь тестируется без единой генерации.
- Ошибки машиночитаемы: `error`, `required`, `granted`, `request_id`, а на 422 —
  карта `details: {поле: [сообщения]}`.
- Описания MCP-инструментов содержат правильные советы: «Всегда передавай
  `idempotency_key`», «Перед вызовом сделай `estimate_generation`». Пробел ровно
  один — флаг безопасности из §1.

## Приложение: воспроизведение

Все измерения бесплатны и повторяются с ключом уровня `read` + `generate`.

```bash
# §3, §4, §5 — расхождения каталогов
curl -H "Authorization: Bearer $TOKEN" https://lk.vibemarketolog.ru/api/agent/capabilities
curl -H "Authorization: Bearer $TOKEN" https://lk.vibemarketolog.ru/api/agent/prices

# §2 — valid: true при непустом rejected
curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"type":"video","model":"grok-ttv-10","prompt":"a cat",
       "image_input":["https://example.com/a.png"]}' \
  https://lk.vibemarketolog.ru/api/agent/generate/estimate

# §6 — duration не влияет на цену
#   тот же запрос с "duration": 1 и "duration": 15

# §1 — схема MCP-инструментов
curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}' \
  https://lk.vibemarketolog.ru/api/mcp
```

Баланс до и после полного прогона: **600 ₽ → 600 ₽**.
