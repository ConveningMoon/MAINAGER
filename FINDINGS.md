# FINDINGS — разбор Agent API

Измерения от 28.07.2026. `GET /health` отдаёт `api_version: 1.0.0`, MCP-сервер
представляется как `vibemarketolog 1.1.0`, протокол `2025-06-18`.

## Как это делалось

Ключ с правами `read` + `generate` — то есть тот, который получает любой новый
интегратор. Первым делом выгрузил `/capabilities` на диск, рассчитывая руками
перенести в код таблицу «какое поле у какой видео-модели отвечает за исходную
картинку». Оказалось, переносить нечего: каталог уже отдаёт `required`,
`optional`, `enums`, `limits`, `tiers`, `tier_prices`, `price_formula` и даже
`mutually_exclusive` по каждой модели. Реестр можно генерировать, а не писать.

Дальше я начал сверять каталог с `/prices` — и вот тут посыпалось.

Всё, что ниже, получено бесплатно: `GET`-эндпоинты, `POST /generate/estimate`,
`POST /webhook-test`, `POST /safety-check` и оба MCP-эндпоинта. Баланс до
прогона — 600 ₽, после — 598,8 ₽. Все девять находок ниже доказаны бесплатно;
1,2 ₽ ушли на отдельную пару вызовов, которой проверялось единственное
утверждение, не проверяемое иначе (см. `COSTS.md`). Это часть вывода: почти всё,
что описано дальше, ваш API рассказывает о себе сам, бесплатно, просто в полях,
на которые агент не смотрит.

Где число получено моделированием, а не замером, я это пишу прямо в строке.

## 1. Через MCP флаг `strict` не виден

Это главное, что я нашёл, и, судя по всему, самое дешёвое в исправлении.

Ваша документация называет одну ошибку самой частой:

> «Самая частая ошибка агентов — слать `image_input` для видео. […] Видео-модели
> его не читают → вы получите чистый text-to-video, а деньги спишутся.»
> — `/docs/agent-api`

И тут же даёт средство:

> «Без `strict` запрос выполнится, но в ответе появится поле `ignored_params` со
> списком отброшенных полей.»

Средство рабочее, я его проверил. Проблема в том, что через MCP до него не
добраться по схеме. Вот что отдаёт `tools/list`:

```
estimate_generation  properties: type, model, prompt, params
                     required:   [type, model]
generate_content     properties: type, model, prompt, params,
                                 webhook_url, idempotency_key
                     required:   [type, model]
```

`params` описан как «Параметры модели из `list_capabilities` (`aspect_ratio`,
`image_urls`, `duration`, `quality` и т.д.)», то есть как параметры модели.
`strict` — не параметр модели, это флаг уровня запроса, и в схеме его нет.

Нет его и в описаниях инструментов, и в поле `instructions` самого MCP-сервера,
где расписан весь рекомендуемый сценарий: `list_capabilities` →
`estimate_generation` → подтверждение пользователя → `generate_content` с
`idempotency_key` → опрос `get_generation_status`. Я на всякий случай проверил
ещё и страницу `vibemarketolog.ru/connect`, которой вы коннектор рекламируете —
слова `strict` там тоже нет.

Три вызова `estimate_generation` с одним и тем же телом, отличается только
способ передать флаг:

| Аргументы | Ответ |
|---|---|
| `params: {image_input: [...]}` | `valid: true`, `rejected: ["image_input"]`, `estimated_cost_rub: 196` |
| `params: {image_input: [...], strict: true}` | `valid: false` |
| `strict` аргументом верхнего уровня | `valid: false` |

Защита достижима — если угадать недокументированный ключ внутри свободного
объекта. Агент читает схему; в схеме ключа нет.

Что из этого следует практически. Агент, который честно идёт по вашим же
`instructions`, вызовет `estimate_generation`, получит `valid: true`, покажет
пользователю смету на 196 ₽, получит подтверждение — и спишет 196 ₽ за ролик,
который проигнорировал картинку. Замер: **196 ₽ за один такой вызов**
(`grok-ttv-10`). Умножать на объём не буду, данных по трафику коннектора у меня
нет.

Лечится добавлением `strict` в `inputSchema` обоих инструментов, по умолчанию
`true`. Это строчка JSON Schema на инструмент. Минимальный вариант — упомянуть
флаг в `instructions`, где остальной сценарий уже описан подробно.

## 2. `/generate/estimate` отвечает `valid: true` на запрос, который сам же бракует

То же самое на уровне REST. Тело с `image_input` для видео-модели, без `strict`:

```json
{"valid": true, "dry_run": true, "model": "grok-ttv-10", "type": "video",
 "estimated_cost_rub": 196, "balance": {"current": 600, "after": 404},
 "rejected": ["image_input"],
 "warnings": ["image_input is for type=image only. For image-to-video use
   image_urls[] with veo/kling/grok, first_frame_url with seedance, or
   character_image_url + reference_video_url with motion-control."]}
```

`valid: true` и `rejected: ["image_input"]` приехали в одном ответе. С
`strict: true` тот же запрос даёт `valid: false`.

Проверка у вас есть, и работает она правильно — весь нужный вывод лежит в
`rejected` и `warnings`. До поля `valid` он просто не доходит, а ветвиться агент
будет именно по `valid`: оно булево и так называется.

Позже я наткнулся на ту же проблему с другой стороны. Прогоняя через смету
корректные тела для всех видео-моделей, получил `valid: false` на четырёх —
`kling-3.0-pro`, `seedance-2`, `seedance-2-fast`, `veo3`. Тела были в порядке:
`validation.media` показывал `ok: true`, `required_missing` пуст, `rejected`
пуст. Причина нашлась в `warnings`:

```
"insufficient_balance: need 1188₽, have 600₽."
"daily_spend_limit would be exceeded."
```

То есть `valid: false` означало «не по карману», а не «запрос неправильный».

Получается, `valid` смешивает два независимых вопроса: корректно ли составлено
тело и хватит ли денег. В первом случае он говорит «да» на сломанный запрос, во
втором — «нет» на исправный. Ни на один из двух вопросов по нему ответить
нельзя, а других полей с булевым ответом в ответе нет.

Я бы разделил: `valid` — только про форму тела, `affordable` — только про
деньги. Плюс `valid: false` при непустом `rejected` независимо от `strict`, а
сам `strict` пусть управляет поведением `/generate`, а не dry-run. Если ломать
существующих клиентов не хочется, хватит и одного нового поля рядом.

У себя я в итоге `valid` не использую вообще: считаю тело чистым по пустому
`rejected`, а доступность — по `warnings` и `daily_spend.within_limit`.

## 3. `price` в каталоге — не цена вызова

Для `grok-ttv` каталог отдаёт `price: 36`, а рядом `tier_prices` с 196 и 316.
Замеры через `estimate`:

```
grok-ttv 36 ₽ · grok-ttv-10 196 ₽ · grok-ttv-20 316 ₽ · grok-ttv-30 436 ₽
```

Разброс — **12×**. В каталоге про это сказано, в `price_note`: «price = цена при
дефолтных параметрах; итог зависит от duration/тира». Но это строка на русском
внутри JSON, а поле называется `price`, и код будет читать поле.

Переименовать в `price_from` — и вопрос закрыт.

## 4. `/capabilities` и `/prices` расходятся

Сверил полные списки идентификаторов из обоих эндпоинтов:

| | Кол-во | Идентификаторы |
|---|---|---|
| Генерируется, но цены в `/prices` нет | 4 | `seedream-5-pro`, `seedream-5-pro-edit`, `motion-control-720p`, `motion-control-1080p` |
| Цена есть, в каталоге модели нет | 7 | `grok-itv-30`, `grok-ttv-30`, `my-voice-tts`, `seedream-5-lite-edit`, `resize-2k`, `resize-4k`, `suno-voice-create` |
| Категория не совпадает | 2 | `gemini-omni-audio` (voice / text), `gemini-omni-character` (image / text) |

Числа в таблице — на момент последнего замера. За один рабочий день 28.07 я
наблюдал категорию `voice` в `/prices` в трёх разных состояниях:

| Замер | Моделей в `voice` | Всего ключей | `hidden_non_generation_keys` | Расхождение |
|---|---:|---:|---:|---|
| утро | 5 | 50 | 88 | 5 без цены |
| вечер | 2 | 47 | 88 | 8 без цены |
| поздний вечер | 7 | 52 | 92 | 4 без цены |

Между вторым и третьим замером вернулись `el-tts-turbo`,
`el-tts-multilingual-v2`, `el-dialogue-v3`, `el-sound-fx-v2` и появился новый
`my-voice-tts`. В момент, когда их не было в прайсе, они прекрасно считались
сметой — то есть из продажи не выводились.

Каталог `/capabilities` за то же время не изменился ни на байт: те же 45
моделей, тот же diff. Двигается только прайс.

Вывод не в том, что кто-то ошибся. Вывод в том, что **расхождение живое**: оно
меняется в обе стороны за часы. Разовая сверка тут не помогает, проверять нужно
на старте каждого процесса. У меня это отдельная команда, `mainager drift`.

Дороже всего обходится вторая строка. Потолок расходов, собранный по
`tier_prices` из каталога, упирается в 316 ₽. Реальный максимум —
`grok-itv-30` за 436 ₽, и `estimate` его спокойно считает. **Ограничитель,
построенный по вашему же каталогу, занижен на 38%** и пропускает самый дорогой
тариф.

Здесь же признаюсь в собственной ошибке: увидев `seedream-5-pro` в первой
строке, я сначала записал, что модель нельзя оценить. Проверил через
`estimate` — оценивается корректно, 40 ₽. Так что вывод другой и он мягче:
неполон не API, неполон `/prices`. Единственный источник цены, который сошёлся
на всех проверенных моделях, — `/generate/estimate`.

### Цифры в `/prices` вдобавок в разных единицах

Это я нашёл случайно, уже собирая смету сценария: озвучка встала в 6 ₽ (утренний
замер), хотя в `/prices` у `el-tts-turbo` стоит 29. Прогнал модели по длине
текста — числа в таблице ниже вечерние, к тому времени тариф успел измениться:

| Символов | `el-tts-turbo` | `gemini-flash-tts` | `el-tts-multilingual-v2` | `my-voice-tts` |
|---:|---:|---:|---:|---:|
| 1000 | 8 ₽ | 13 ₽ | 39 ₽ | 10 ₽ |
| 1001 | 16 ₽ | 26 ₽ | 39 ₽ | 20 ₽ |
| 2500 | 24 ₽ | 39 ₽ | 39 ₽ | 30 ₽ |
| 5001 | 48 ₽ | 78 ₽ | 39 ₽ | 60 ₽ |
| **в `/prices`** | **29 ₽** | **13 ₽** | **39 ₽** | **29 ₽** |

Три разные величины в одной колонке: у `gemini-flash-tts` это цена за начатую
тысячу символов, у `el-tts-multilingual-v2` — цена за вызов целиком, а у
`el-tts-turbo` и `my-voice-tts` — числа, которых не видно ни на одной длине.
У `my-voice-tts` расхождение самое прямое: **в прайсе 29 ₽, по смете 10 ₽**,
причём обе цифры отдаются живым API в одну и ту же минуту.

**И сами цены двигаются в течение дня.** Первый замер `el-tts-turbo` утром
28.07 дал 6 / 12 / 18 / 36 ₽ на тех же длинах — то есть 6 ₽ за начатую тысячу.
Вечером того же дня — 8 ₽ за тысячу, рост на треть. В `/prices` при этом всё те
же 29 ₽. Я привожу оба замера, потому что вывод именно в разнице: **любая
статическая таблица цен, ваша или наша, устаревает за часы. Актуальна только
смета в момент вызова.**

Три разные вещи в одной колонке. У `gemini-flash-tts` это цена за начатую
тысячу символов, у `el-tts-multilingual-v2` — цена за вызов целиком, а у
`el-tts-turbo` — 29 ₽, которых я не увидел ни на одной длине.

Практический эффект: агент, выбирающий самую дешёвую озвучку по `/prices`,
возьмёт `gemini-flash-tts` за 13 ₽ вместо `el-tts-turbo` за 8 ₽. Список цен
переворачивает порядок — и продолжает переворачивать даже после того, как
реальный тариф вырос с 6 до 8 ₽: в `/prices` по-прежнему 29.

Я бы добавил в `/prices` поле с единицей измерения (`per_call`,
`per_1000_chars`, `per_second`). Сейчас числа в этом списке между собой просто
несравнимы, а выглядят сравнимыми.

## 5. Каталог противоречит сам себе

В одном и том же ответе `GET /capabilities`:

```
getting_started.image_to_video      →  "grok-itv-10|20|30"
models.video["grok-itv"].tiers      →  ["grok-itv-10", "grok-itv-20"]
```

Три тарифа в текстовой подсказке, два в машиночитаемой части. Пропущенный —
самый дорогой. Реестр, собранный из `models[].tiers`, про `-30` не узнает, а
whitelist, собранный оттуда же, отклонит валидный запрос.

## 6. Ваш же пример в документации делает вызов дороже в 8,8 раза

Начал я с того, что зафиксировал тариф в идентификаторе — `grok-ttv-10`, как
показано у вас в `getting_started`, — и померил цену на разных длительностях:

```
duration= 1  → 196 ₽        duration=10  → 196 ₽
duration= 5  → 196 ₽        duration=15  → 196 ₽
```

Плоско. Записал вывод «`duration` на цену не влияет» и пошёл дальше. Вывод
оказался неверным: он верен только для закреплённого тарифа.

Тот же замер на базовом идентификаторе, без суффикса:

```
grok-ttv,  duration 1…6   →  36 ₽
grok-ttv,  duration 7…10  → 196 ₽
grok-ttv,  duration 11…15 → 316 ₽
```

То есть `duration` на базовом id — это и есть выбор тарифа, и делается он
автоматически, по минимально достаточному. `grok-itv` ведёт себя так же.

А дальше сравнение, ради которого всё это писалось. Ролик на 5 секунд:

| Как позвать | Цена |
|---|---|
| `model: "grok-itv"`, `duration: 5` | **36 ₽** |
| `model: "grok-itv-10"`, `duration: 5` | 196 ₽ |
| `model: "grok-itv-20"`, `duration: 5` | 316 ₽ |

Одна и та же длительность, разница **8,8×**. При закреплённом тарифе `duration`
принимается, не попадает в `rejected`, присутствует в `valid_params` — и
игнорируется. Дефект из §2 во втором месте.

Неприятная часть: `getting_started.image_to_video` показывает агенту именно
закреплённую форму — `"grok-itv-10|20|30"`. Интегратор копирует пример из
документации и получает самый дорогой из возможных способов заказать короткий
ролик.

Я бы поменял пример на базовый идентификатор и написал прямо, что длительность
сама выберет тариф. Если закрепление тарифа — осознанная возможность, тогда
`duration` при нём стоит возвращать в `rejected`, чтобы было видно, что он не
действует.

## 7. Каталоги неполны в обе стороны

`capabilities.endpoints` перечисляет 28 путей. Работают и отвечают 200, но в
списке отсутствуют `GET /me`, `/health`, `/capabilities`, `/generations` и
`/inbox`. Последний заметнее прочих — на нём строится входящий канал.

В обратную сторону: `/docs/agent-api` описывает `omnihuman-1-5` и
`volcengine-lipsync` вместе с их полями, а в `/capabilities` их нет ни в одной
из четырёх категорий.

Отдельно про «170+». Каталог отдаёт 45 генеративных моделей, `/prices` — 50
ключей и признаётся: `hidden_non_generation_keys: 88`, чат и посекундные тарифы
считаются отдельно. 45 + 88 ≈ 133, так что публичная цифра взята не с потолка.
Но агенту доступны 45, и себестоимость сценария считается по этому числу.
Развести бы эти две цифры явно, иначе интегратор планирует под поверхность
крупнее реальной.

## 8. Латентность агента — это строка в P&L, а не техническая метрика

Это лежит в разделе про Bitrix24 и, судя по всему, читается редко. Ваша
тарификация входящих:

> «Доставка сообщений и ответы ВАШЕГО агента (inbox/webhook) — бесплатны (входят
> в тариф). Если агент не забрал сообщение и ответил авто-ответчик платформы
> (`reply_source=platform`) — списание с баланса владельца по прайсу текстового
> чата: 10 ₽/ответ, страховочный — 8 ₽/ответ.»

И порог срабатывания:

> «Авто-ответчик: если агент не забрал сообщение за ~4 секунды, платформа
> отвечает сама от имени агента.»

Ответ агента — 0 ₽. Ответ платформы за него — 10 ₽. Решают четыре секунды.

Клиент в чате разницы не видит: ответ приходит в обоих случаях. Владелец аккаунта
видит только итоговый счёт. Никакой строки «мы заплатили за то, что агент не
успел» в интерфейсе нет.

Я не буду умножать это на выдуманный объём — данных по трафику коннектора у меня
нет. Важен метод: **каждая секунда сверх четырёх имеет цену, и её можно
посчитать.** Владельцу аккаунта достаточно посмотреть долю ответов с
`reply_source=platform` за месяц.

Практический вывод для архитектуры: короткий осмысленный ответ за 3 секунды с
подробностями вторым сообщением дешевле, чем один полный ответ за 6 секунд —
на 10 ₽ за сообщение. Разбор этого решения — в [`DESIGN.md`](DESIGN.md).

## 9. Слово «edit» в названии модели стоит дороже и ничего не гарантирует

Логично предположить, что доработать готовую картинку дешевле, чем нарисовать
новую. Я это проверил, и оказалось наоборот.

Специальные `*-edit` варианты стоят **дороже** своих базовых моделей:

| Базовая | Цена | Вариант `-edit` | Цена | Разница |
|---|---:|---|---:|---:|
| `gpt-image-2` | 19 ₽ | `gpt-image-2-edit` | 22 ₽ | +3 ₽ |
| `seedream-5-lite` | 15 ₽ | `seedream-5-lite-edit` | 18 ₽ | +3 ₽ |
| `seedream-5-pro` | 40 ₽ | `seedream-5-pro-edit` | 45 ₽ | +5 ₽ |

При этом девять обычных моделей принимают `image_input` и делают ровно ту же
операцию — правку существующего изображения — **по цене генерации с нуля**:

```
nano-banana-2-lite   txt2img  9 ₽    img2img  9 ₽
nano-banana-2-1k     txt2img 15 ₽    img2img 15 ₽
seedream-4.5         txt2img 15 ₽    img2img 15 ₽
```

Итог: правка картинки через `seedream-5-pro-edit` — 45 ₽, через
`nano-banana-2-lite` — 9 ₽. **Разница в 5 раз** за один класс операции.

Добавляет к этому каталог: у **всех** моделей, принимающих `image_input`,
включая сами `-edit`, стоит `preserves_input: false`. То есть за наценку в 3–5 ₽
вы не получаете и байтовой сохранности оригинала — её не обещает никто.

Понятно, что качество у моделей разное и сравнение не «одно и то же за разные
деньги». Проблема в навигации: человек, которому нужно «отредактировать
картинку», ищет слово edit и приходит к самому дорогому варианту. Ни в каталоге,
ни в документации не сказано, что обычная модель с `image_input` делает то же
самое дешевле.

Я бы написал в описании `-edit` моделей, чем они отличаются от `image_input` у
обычной модели. Если ничем, кроме качества — так и сказать, указав, что дешёвый
путь существует.

## Что сделано хорошо

Несколько вещей я, наоборот, не ожидал увидеть и хочу отметить.

`POST /generate/estimate` бесплатен и точен. Он корректно оценил всё, включая
модели, которых нет в `/prices`, и тарифы, которых нет в `tiers`. По сути это
лучший эндпоинт в API, и половина проблем выше решается фразой «считайте цену
только им» в документации.

`pre_charge_validation` — не декларация. Недоступный `image_urls` возвращает
`{"ok": false, "code": "unreachable", "http": 404}` и сбрасывает `valid` в
`false` ещё на этапе сметы. Бесплатно.

Ответ `estimate` заодно отдаёт `balance.{current, after}` и
`daily_spend.{limit, today, within_limit}` — этого достаточно, чтобы посчитать
стоимость целого многошагового сценария, не потратив ни рубля.

`POST /webhook-test` отдаёт реальную диагностику доставки вместе с формулой
подписи, так что весь webhook-путь тестируется без единой генерации.

Ошибки машиночитаемы: `error`, `required`, `granted`, `request_id`, а на 422 —
карта `details: {поле: [сообщения]}`. С таким набором клиент пишется нормально.

И в описаниях MCP-инструментов советы правильные: «Всегда передавай
`idempotency_key`», «Перед вызовом сделай `estimate_generation`». Не хватает там
ровно одного флага — того самого, из §1.

## Как воспроизвести

Всё бесплатно, ключа уровня `read` + `generate` достаточно.

Самый короткий путь — не curl, а команда:

```bash
pip install -e ".[mcp,dev]"
mainager verify
```

Она заново отправляет запрос за каждым из девяти пунктов ниже и печатает,
совпадает ли текущий ответ API с тем, что записано здесь. Ручные `curl` под
каждым пунктом — на случай, если нужно посмотреть на сырой ответ самому.

```bash
# §3, §4, §5 — расхождения каталогов
curl -H "Authorization: Bearer $TOKEN" https://lk.vibemarketolog.ru/api/agent/capabilities
curl -H "Authorization: Bearer $TOKEN" https://lk.vibemarketolog.ru/api/agent/prices

# §2 — valid: true при непустом rejected
curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"type":"video","model":"grok-ttv-10","prompt":"a cat",
       "image_input":["https://example.com/a.png"]}' \
  https://lk.vibemarketolog.ru/api/agent/generate/estimate

# §6 — тот же duration: 5, разные идентификаторы модели.
#      "grok-itv" → 36 ₽, "grok-itv-10" → 196 ₽, "grok-itv-20" → 316 ₽

# §1 — схема MCP-инструментов
curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}' \
  https://lk.vibemarketolog.ru/api/mcp
```

Баланс: 600 ₽ до разбора, 598,8 ₽ после. Всё, что перечислено выше, —
бесплатно; 1,2 ₽ списаны отдельной проверкой из `COSTS.md`.
